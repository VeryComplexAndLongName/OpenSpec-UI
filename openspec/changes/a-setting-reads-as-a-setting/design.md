# Design

## Decision: the tokens come first, and nothing draws a literal colour

`shellThemeCss` has twelve custom properties and 153 uses of them —
and 21 further colours written as literals in the rules themselves, 29
times. A new palette applied on top of that comes out patchy in exactly
the places nobody looks at twice: a diff's added-line tint, an event
row's left edge, a disabled button.

So the first half of this change is mechanical and has no visible
result: every literal moves into `:root` under a name that says what it
is for, not what colour it is. `--diff-added-bg`, not `--pale-green`.

That ordering matters for a second reason. `vscodeThemeCss` redefines
the same names against the editor's theme variables, so a token that
exists only in the shell layer renders the extension's panel with a
missing value. Every token this change adds gets a mapping there in the
same commit, and a test walks the shell's `:root` and asserts the
extension layer defines every name in it — the check that keeps the two
from drifting, which today nothing does.

## Decision: the name belongs to its control, by proximity and by weight

A label 6px from its own control and 12px from the previous one belongs,
to the eye, to the previous one. The gap within a field becomes smaller
than the gap between fields, which is the whole of the fix, and the
label gains weight and a slight tracking so that it reads as a name
rather than as another remark in the same grey.

Deliberately not colour alone. The shell must pass the axe run in the
browser suite at WCAG AA, and a label distinguished only by being paler
is both a contrast risk and unreadable to anyone who cannot see the
difference.

Where a row is a name and a value and nothing else — the stage rows, the
mechanical stages — the label moves into its own column. A settings pane
is a two-column document; making it one is what stops the page reading
as an undifferentiated stack.

## Decision: a control is as wide as its value

`width: 100%` on every input is the reason a dropdown holding `high` is
900px wide, and the reason its arrow is 900px from the word. Controls
get widths from the kind of value they hold: an agent id, an effort
word, a cost, a sentence-long autonomy level. Four sizes, named, not a
number per field.

This is also the accessibility fix nobody asked for: a 900px target for
a five-character value means the pointer travels the full width of the
page to reach the arrow.

## Decision: editor-native, and what that rules out

The look is a settings pane: low contrast between surfaces, radius small
enough to soften a corner rather than announce a card, one shadow spent
on the things that genuinely float, and a type scale that stays out of
the way. The full comparison and the three rejected directions are in
ADR 0023.

The reason in one line: this product has dense forms and long prose —
proposals, timelines, streamed agent output — and the directions that
were more characteristic each fought one of the two. A look you stop
noticing is the right outcome for a window that stays open while agents
run.

"Not everything is a card" is the operative rule. Today every block
carries the same border, radius and shadow, which flattens the hierarchy
to nothing: the headline, the tab strip, a panel and a list row all look
equally important. Border and fill separate; shadow is reserved for what
overlays.

## Decision: the screenshots are regenerated, not hand-updated

`harness-screenshots.spec.ts` and `change-charts.spec.ts` write the
images under `docs/images/standalone/` from the running UI. They are
regenerated by running the suite, and the diff is reviewed as part of
this change rather than described. A documentation screenshot that
disagrees with the product is the failure that spec exists to prevent.

## Non-Goals

The extension's own appearance. New capabilities. Rearranging what is on
any screen, including the Harness Settings template list, which is four
dense paragraphs inside bullet points and is its own piece of work.

## Risks / Trade-offs

Contrast. A quieter palette is the easiest way to fail WCAG AA, and the
browser suite's axe run is the gate. Every pair is checked against it,
and the muted text token in particular is set from the contrast
requirement rather than from taste.

Every screenshot in the documentation changes in one commit, which makes
the diff large and hard to read. That is unavoidable for a restyle and
is the reason the spec generates them rather than anyone editing them.

The look is deliberately unremarkable, and unremarkable is the one
quality nobody thanks you for. Recorded in the ADR so that it reads as
the decision it is.
