## Context

Read on 2026-09-03:

- `WorkbenchRunJournal.load()` iterates `document.checkpointSessions` and
  awaits `resolveCheckpointSession` for each, which `readFile`s and
  `JSON.parse`s that reference's file. Sequential, and awaited by
  `activate()`.
- `write()` keeps a session for any process inside `maxProcesses`
  (default 100), regardless of state.
- `pruneCheckpointFiles(retainedIds)` deletes only files not in
  `retainedIds`, and every retained session is in it.
- `ImplementationSessions.restore()` deserializes every session, but only
  *uses* the checkpoint immediately when the process is `interrupted` and
  has no delta — the rest sit in memory until a rollback is requested.
- `WorkbenchRecoveryService` reports `canRollback` for `completed`,
  `failed` and `interrupted`.

## Goals / Non-Goals

**Goals:**

- Activation cost independent of how many checkpoints are on disk.
- A bound on retained checkpoints that does not depend on anything else
  staying small.

**Non-Goals:**

- Reducing the size of a single checkpoint.
- Changing rollback eligibility.

## Decisions

### Retention is by count, not by process state

Keep the N most recent checkpoint sessions, whatever state their process
is in.

**Rejected alternative**: drop the checkpoint as soon as its process
reaches a terminal state, keeping only `interrupted` ones. This was the
first instinct, and it is wrong: `canRollback` is
`["completed", "failed", "interrupted"]`, so a terminal run is precisely
one the recovery view still offers to roll back. A state-based rule would
silently remove a capability the product documents, which is the class of
defect this repository has spent the week deleting.

That mistake was made in practice before it was caught here. Pruning this
repository's own directory by process state on 2026-09-03 freed 502.8 MB
and, with it, the rollback of 24 past runs — harmless, because all of
them were already merged, and instructive, because the reasoning that
justified it ("nobody rolls back a completed run") was contradicted by the
code.

### Checkpoint retention gets its own number

`maxProcesses` cannot serve both. A process entry is tens of bytes and a
hundred of them is a useful history; a checkpoint is tens of megabytes and
a hundred of them is two gigabytes. One limit over two quantities that
differ by six orders of magnitude is not a limit.

**Rejected alternative**: a byte budget for the directory rather than a
count. Rejected as more machinery than the problem needs — it means
stat-ing every file on every write to decide what to evict, and the count
is what a person can reason about when they read the setting.

### `load()` returns references and a reader

The journal already stores references. `load()` hands them back with a
function that reads one payload on request, so nothing pays for a
checkpoint it does not open.

**Rejected alternative**: keep `load()` eager but run the reads in
parallel. Rejected — it makes half a gigabyte of I/O concurrent rather
than unnecessary, and turns a slow activation into a slow activation that
also competes with everything else the window is doing at that moment.

**Rejected alternative**: read payloads in a background task after
activation returns. Rejected — activation would finish quickly while the
work still happens, so the cost moves out of the measurement rather than
out of the product. It also introduces a window where a restored session
exists but its checkpoint does not.

### The interrupted-process path still resolves at startup

`restore()` finalizes a checkpoint for a process that is `interrupted`
with no delta, and that has to keep happening at startup: it is what turns
an interrupted run into a reviewable one. Those are few — five of
twenty-nine here — and reading five files is not what made activation
slow.

## Risks / Trade-offs

- **[Risk]** A lazily-resolved checkpoint can fail to read at the moment
  the user asks for a rollback, where before it failed at startup. →
  **Mitigation**: the failure surfaces where the request was made, which
  is where a person can act on it; a startup failure for a rollback
  nobody asked for is the worse of the two.
- **[Trade-off]** A retention count means an old enough run loses its
  rollback. Accepted, and it is the point: today nothing loses it, and
  the cost is paid by every window open.

## Open Questions

- The retention count itself. Twenty keeps roughly a day of this
  repository's own activity at about 400 MB, which is still a lot of disk
  for something regenerated by the next run. Ten is likelier right. The
  tasks require whichever number is chosen to be stated with its measured
  consequence rather than picked.
