# Design

## Goals

The Harness asks before its own opted-in remote write regardless of whether the agent asked a question. The operator sees exactly what would be pushed and can authorize that one attempt.

## Non-Goals

- Intercept commands run inside external agents or cover `Create Change`, `Commit Change`, PR creation, merging, or automated branch maintenance.
- Change how an operator answers design questions or build a general approval engine for arbitrary shell commands.

## Decisions

### Policy lives beside the existing allowlist

Add the optional boolean `gitStageAllowlist.requirePushApproval` to the per-change config and generated schema. Missing or false selects the existing path. In the opted-in path, perform the existing allowlist decision before asking and check it again before executing. A denial ends the stage before a push or any later Git action. A refused push follows the existing failure path.

After committing what the stages left, prepare a normal, single-ref push from the full source commit ID to a full branch ref at one effective push endpoint. Show the remote and a credential-free repository identity. Bind execution to the prepared source and destination. Resolve the effective destination again before dispatch, and invalidate the request on drift in the commit, branch, endpoint or applicable policy. If the runtime cannot pin a single destination, it refuses the push. Suppress additional tag and submodule pushes and reject mirror, force and deletion modes in this path. Use Git's normal fast-forward rules and the remote's protections.

We rejected making agent question markers a precondition. They are generated by the model and carry neither a verified operation nor its target. We rejected offering an approval for an action outside the allowlist because that would create an override path.

### Reuse the permission exchange

Use the existing `permissionRequest` event and `resolvePermission` command. Add optional typed `pushApproval` details to the event with the source commit, remote, credential-free repository identity and full destination ref. Keep the existing description complete so VS Code and standalone clients that already render permission requests can show and resolve the prompt. Existing ACP permission events and resolution behavior retain their current shape. Harness-owned requests are routed to a pending approval in Core before the adapter path. Unlike an agent permission request in autonomous mode, a Harness push approval waits for an operator in every mode. Status and logs use the existing permission waiting state.

Use a fresh request ID per attempt and bind it to the run and the prepared push. Register the pending request before emitting it. An Allow or Deny consumes that request once. Stop, cancel, or losing the in-memory run expires it. Treat a changed action as a fresh approval if retried. Record request, decision, invalidation and push outcome without storing credentials. Audit data and `decisions.md` are never read as permission grants.

Interactive CLI runs answer this typed request using their existing terminal prompt. If the terminal cannot ask, fail with a reason and cancel the pending request. An unattended caller cannot obtain an implicit Allow.

We rejected reusing a stage checkpoint because confirming the run ID alone cannot distinguish two pending actions across attempts. We rejected persisting approvals across restarts because the action may have changed since the operator saw it.

## Risks / Trade-offs

- A configured push adds a human stop to an otherwise autonomous chain. Headless runs must use an approval-capable host or end before the remote write.
- The allowlist applies to actions the Harness executes. An agent that invokes Git in its own process is governed by that agent's sandbox and permissions.
- The normal push can still be rejected after approval. A retry goes through the policy with a fresh request.
