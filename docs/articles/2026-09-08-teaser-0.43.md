I shipped a feature that showed exactly the right thing and saved none of it.

Three named configurations for an agent harness — Minimum cost,
Balanced, Fastest — each setting spending and time ceilings drawn from
measured runs. You pick one. The form fills. The diagnostic panel recomputes and
agrees. A message says, truthfully, "nothing is saved until you save."

Then you save, and every ceiling is gone.

The settings view sent two of the eight accepted configuration keys, and
the writer replaces the file. So everything a template exists to set was
deleted on the way out — the timeouts, the budgets, the attempt counts,
and the list of paths the agent is allowed to stage.

![The per-change settings section, with the three named configurations](../images/standalone/harness-change-override.png)

No test caught it. Every test looked at the half that was correct.

That turned out to be the shape of four separate defects in one release
cycle, all found the same way: by a person opening the file that came out
and reading it.

The unattended template promised "no checkpoints between stages" and its
configuration never said so, so it paused at every one. A chain's verify
stage was built to send unfinished work back to apply — and the gate in
front of it returned "failed" before the code could ever run, making the
one case it was written for the one case it could not reach. A run cut by
a time limit showed the reason on screen and wrote nothing to the audit
log, so in the permanent record a run stopped by a rule looked exactly
like one a person cancelled.

Four different bugs. One shape: the visible half was right and the
acted-upon half was not.

A test that checks the visible half passes every single time.

![The Run dialog: the resolved path, the setting it read, each stage's agent, and the ceilings that cannot act](../images/standalone/run-dialog.png)

So 0.43 does the opposite. There used to be two menu entries for starting
work, and which one you wanted was a value in a file that one of them
never read. Picking wrong wasn't visibly wrong — on some changes it just
looked like the button switched tabs.

Now there is one entry, and before it starts anything it says what it
read: which path will run and which setting decided that, which agent
runs each stage, which stages have no agent at all, which of your
ceilings cannot act — because six of the ten supported agents report no
usage, so a cost limit over them is decoration — and which named
configuration it recommends, with the observations behind it and a button
to apply it.

That screenshot is captured from the running product by an end-to-end
test, on the commit it illustrates. Taking it found a fifth defect: the
two lists rendered as one undifferentiated run of bullets. No assertion
would have reported that either.

The lesson I keep relearning: a ceiling that cannot act is worse than no
ceiling, because it reads as protection.
